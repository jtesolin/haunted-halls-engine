## Claude Code role separation

- The main Claude Code session is the implementation owner for the current issue/PR/worktree.
- Once the `haunted-halls-dev-loop` is active for a PR, keep that loop active across follow-up user messages and remediation pushes until the user explicitly pauses/cancels it, the loop escalates, or it reaches `READY FOR HUMAN VALIDATION`.
- The Claude dev loop is single-writer per PR: only one Claude implementation session may own an active loop for a PR at a time. The durable retry-state protocol is not a distributed lock; if concurrent implementation ownership is known or suspected, escalate instead of continuing or using last-write-wins state.
- Use the `haunted-halls-dev-loop` skill for the implementation -> independent review -> director disposition -> remediation workflow. Before implementing a material user-visible/cross-repository capability, it must verify the intended supported production lifecycle and required state producers; a prerequisite already in the current durable scope may be implemented normally, while a capability that would remain unreachable because of an out-of-scope missing prerequisite requires escalation unless an explicitly staged incomplete state has durable scope and explicit human approval.
- Use the `haunted-halls-reviewer` subagent for independent code review. It must start from fresh context, explicitly map issue acceptance criteria and trusted-base completion requirements, inspect architectural fit and end-to-end production reachability/state producers/cross-repository prerequisites, inspect material helper semantics/adversarial boundaries, verify documented deterministic edge cases with discriminating tests, and inspect material changed query/index risk. It must not edit files.
- Use the `haunted-halls-director` subagent after every reviewer result, including a clean review, to classify findings and verify that material review coverage and architectural viability are sufficient. Acceptance-criterion/completion findings cannot be deferred merely for low severity; unresolved product semantics or unreachable claimed behavior require escalation. It must not edit files or implement fixes.
- The implementer must not decide whether its own review findings should be accepted; the director owns the coverage/disposition step.
- The main implementation session persists schema-3 Claude review records under `<!-- haunted-halls-claude-review-disposition -->`: intermediate `reservation` records, completed `director` records, and explicit human-authorized `recovery` records. It validates complete record shape, author/owner, matching head/retry SHA, foreign current-head ownership conflicts, monotonic same-head retry history, and sticky terminal escalations. Only a complete nonterminal current-head `director` record can authorize remediation or readiness; reservation/recovery/partial records fail closed. Reviewer and Director subagents remain read-only.
- `.github/agents/local-developer.agent.md` is the VS Code Copilot implementation-agent prompt. Reuse its branch freshness, commit, PR-creation, and scope safeguards where applicable, but the Claude-specific loop and role boundaries live under `.claude/`.
- Durable repository/issue context outranks conversational assumptions. Escalate when durable sources are insufficient or conflicting.
- The user retains final merge authority. Never merge autonomously.
